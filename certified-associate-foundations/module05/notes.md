## Configuration and Knowledge Management
_Configuration is leverage: you set it up once and benefit from it on every conversation that follows_
- turns individual skill into team capability
- two people asking the same question get the same *quality* of answer
- configurations age; well-configured is built deliberately and reviewed on a cadence

### Configuring Projects
_putting each piece of a recurring need into the right configuration slot_
- instructions
	- govern behavior
	- tone, format defaults, verification habits; behavior not facts
- knowledge base
	- holds facts
	- documents, policies, and reference files; facts and reference, not behavior
- skills
	- carry procedures
	- not one-off instruction
	- live at the account level, reusable across any project
- scoped memory
	- keeps continuity
	- kept separate from other projects so context does not bleed between workstreams

a rule about behavior is an instruction, a fact needed is knowledge, and a multi-step procedure is a skill

>scoped memory holds what the project has already settled; stakeholder names, standing preferences, decisions from earlier, etc

a stable reference fact goes in knowledge while an evolving record of decisions goes in memory

configurations rarely map to a single slot
- behavior rule + facts it acts on
- status report skill + brand guide

>when configuring a project ask which slot a need belongs in but also ask if it needs to slots wired together

### Connectors and Upload Knowledge
_reach extenal systems_
- defined boundaries; email allows search and read but not send
- learn the connector's boundaries before building a workflow on it
- keep uploaded knowledge current, relevant, and free of duplicates

### System-Level Instructions
_write verification behavior, format defaults, and tone once, and everyone conversation inherits_
- the highest-value instructions are the ones you would otherwise re-type constantly
- anticipate the use cases; embed format, tone, and guardrail guidance ahead of the need
- the test of an instruction is whether two different people would read it the same way

### Maintaining Configurations
_configurations are living assets_
scheduling maintenance is how you catch a decay before it reaches a deliverable
- review cadence
	- the signal that you waited too long is output quality slipping for no visible reason
- skills versioning
	- a skill that silently produces a slightly off format every run is a maintenance problem, not a prompting problem
- memory lifecycle
	- treat like a working file
	- review periodically, edit or delete stale entries, export a backup before a major change
>configuration is also additive: a constraint, preference, piece of background, etc should be explicitly added to standing instructions or memory when appropriate

# Key Takeaways
#### Configuration is leverage.

Set up once, benefit on every conversation. A configured environment separates operating Claude from merely using it.
#### Match each need to the right mechanism.

Instructions for behavior, knowledge for facts, Skills for procedures, scoped Memory for continuity.
#### Know each connector's boundary.

Connectors extend Claude's reach, but each has a capability edge; knowing it prevents frustration and misrouted fixes.
#### Write instructions precisely.

Vague standing instructions silently fail; precise, testable ones change output every conversation.
#### Maintain or watch quality decay.

Configurations age. Schedule reviews of instructions, knowledge, Skills versions, and Memory, or output degrades with no warning.
